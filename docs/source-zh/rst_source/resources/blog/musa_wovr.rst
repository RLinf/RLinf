RLinf × MUSA：在摩尔线程 S5000 上复现 WoVR
============================================================

本文介绍在摩尔线程 S5000 加速卡上，使用 RLinf 复现 WoVR 世界模型强化学习训练闭环的工程适配与性能实践。从设备识别、模型语义对齐，到权重同步、显存管理，再到单机 8 卡与双机 16 卡优化，逐步说明训练链路如何跑通、瓶颈如何定位。MUSA 是摩尔线程的软件与运行时平台，S5000 是本次实验使用的加速卡。

实验报告中，S5000 与 A100 的 191 步训练成功率曲线相关系数为 0.976；第 190 步的 LIBERO 外部评测成功率分别为 74.6% 和 73.4%。在另外两组性能实验中，8 卡配置优化将整步耗时降低 10.6%，双机混合分片将整步耗时降低 15.3%、权重同步耗时降低约 66%。

.. note::

   本文记录以上游提交 ``4677808a`` 为参照的实验适配，以下实现细节与测量结果均对应这次实验。其中，``WOVR_*`` 开关、``perfA`` 配置和 ``wan_spatial_official_s5000.yaml`` 是实验实现中的名称，并非本文档版本随附的配置选项。当前维护的安装步骤与硬件覆盖范围见 :doc:`Wan 示例 <../../examples/embodied/wan>`。

训练闭环与 GPU 布局
-------------------

迁移首先要保持完整的训练闭环：policy 生成动作，世界模型预测后续状态，奖励再指导下一次 policy 更新。在 :doc:`WoVR <../publications/wovr>` 中，OpenVLA-OFT 每次输出包含 8 个动作的 chunk，Wan 生成后续画面，奖励模型判断任务是否完成，RLinf 再用 GRPO 更新 OpenVLA-OFT。

RLinf 的 worker 分别承载环境交互、policy 推理和参数更新，调度器决定它们运行在哪些 GPU 上，channel 在 worker 之间传递 rollout 数据。权重同步和 FSDP 集合通信则分别处理参数传输与梯度通信。一次训练 step 的数据流可以简化为：

.. code-block:: text

   OpenVLA-OFT (rollout) -- 8 个动作 --> Wan + 奖励模型 (env)
            ^                                  |
            |                         画面、奖励、轨迹
            |                                  v
            +--- 同步新权重 --- GRPO / OpenVLA-OFT (actor)

env、rollout 和 actor 是三个逻辑角色。GPU 布局决定各模型何时驻留显存，以及数据何时需要跨设备搬运。

.. list-table:: 执行布局
   :header-rows: 1
   :widths: 18 42 40

   * - 布局
     - GPU 使用方式
     - 主要取舍
   * - 共享式
     - 各角色轮流使用同一批 GPU，通过 offload 切换模型驻留。
     - placement 简单，但最慢的 rollout 会拖长整步时间。
   * - 分离式
     - 各角色占用独立的 GPU 组。
     - 减少模型换入换出，但数据依赖可能造成 GPU 空转。
   * - 混合式
     - env 与 rollout 分组流水，actor 更新时使用完整 GPU 组。
     - 队列解耦生产与消费，同时增加调度要求。

本次复现采用共享式布局，先在单机 8 卡上验证设备分配、显存驻留和通信，让每项适配都经过同一条端到端链路。三种布局的完整说明见 :doc:`执行模式 <../../concepts/execution_modes>`。

设备识别与分配
~~~~~~~~~~~~~~

第一个问题发生在加载模型之前。目标容器缺少预期的 ``pymtml`` Python 绑定，PyPI 上的同名包又使依赖来源容易混淆。管理库查询失败后，程序把设备数量判为 0。实验适配保留原查询，并在失败时回退到 ``torch.musa.device_count()``。

识别出设备之后，还要确定每个进程使用哪张卡。在本次运行时环境中，若在进程内部把 ``MUSA_VISIBLE_DEVICES`` 重写为 ``0``，可能选中物理 0 号卡，而非预期的本地设备。因此，实验在容器边界通过 ``MTHREADS_VISIBLE_DEVICES`` 限制可见卡，在容器内保留 RLinf 的 rank 管理逻辑。

环境属性与分布式后端
~~~~~~~~~~~~~~~~~~~~

设备分配正确后，初始化又暴露出环境接口不匹配的问题。属性查询优先调用 ``get_wrapper_attr``，但 Wan 环境不是标准 Gym wrapper，这条路径抛出的 ``AttributeError`` 被误判为属性不存在。适配在失败时回退到普通 ``getattr``，保留 wrapper 的属性委托行为。当前的 ``get_env_attr`` 也会在查询失败后沿 wrapper 链继续查找。

分布式初始化则需要同时建立设备后端与 CPU 后端。MUSA 集合通信使用 MCCL，而 checkpoint 的分片 state dict 路径还需要 Gloo。实验实现在创建设备 mesh 前显式初始化二者：

.. code-block:: python

   dist.init_process_group(backend="cpu:gloo,musa:mccl")

这条调用让 CPU tensor 使用 Gloo，MUSA tensor 使用 MCCL。双后端是初始化的前提；断点续训是否完整可用，仍需要独立验证。

对齐 OpenVLA-OFT 的注意力语义
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

进程能够运行，并不意味着 policy 行为正确。OpenVLA-OFT 依赖双向注意力，而未应用 OFT 定制补丁的上游 Transformers 4.40.1 会使用 causal attention。同一训练配置下，修复前 S5000 的第一步成功率为 0；补上 ``is_causal=False`` 和纯 padding mask 后，S5000 达到 0.516，A100 对照为 0.469。

这种语义偏差改变了 policy 分布，使动作接近随机，GRPO 难以获得有效训练信号。因此，必须先对齐注意力行为，再比较数值精度和性能。

通过 CPU 内存同步权重
---------------------

模型行为对齐后，每个训练 step 仍需把约 15 GB 新权重从 actor 组传给 rollout 组。同卡 IPC 与跨卡 ``isend``/``irecv`` 的独立探针可以通过，但 8 卡并发设备直传仍会触发 ``launch timed out``。完整训练同时涉及 GPU 共享、MCCL 和进程隔离，单项探针没有覆盖这种组合。

实验最终采用经过 CPU 内存的稳定路径：

.. code-block:: text

   actor GPU -> CPU buffer -> CPU/Gloo -> rollout CPU -> rollout GPU

权重同步配置选择 ``transport_device: cpu``。这增加了拷贝，但每步只同步一次，而且权重可以分片并行传输。冒烟测试测得约 41 s；在完整参考训练中，权重同步约占整步的 2%。共享式布局下，世界模型生成和 VLA 推理仍是主要耗时。

适配还调整了两处通信边界。由于每个 rank 已独立加载同一份 Hugging Face checkpoint，可以关闭 ``sync_module_states``，避开 7.5B 模型 coalesced broadcast 挂起的问题。权重传输使用 CPU/Gloo，设备集合通信继续使用 MCCL，也避免了依赖未发布的额外通信库。

控制显存驻留与异常 batch
------------------------

通信稳定后，下一个限制是显存：训练模型、推理模型和世界模型同时驻留需要超过 80 GB。实验按阶段调整模型驻留时间，控制峰值占用。

世界模型常驻 env 进程，约占 24.9 GB；rollout 模型在不推理时 offload 到 CPU；env 生成画面期间，actor 的参数和优化器状态也 offload，进入训练阶段再加载回来。这一布局支持了单机 8 卡训练，micro batch 大小仍需根据节点可用显存逐档验证。

并发运行还暴露了偶发的 batch 行级 NaN 或 Inf。实验适配在 VLA 和 Wan 前向中检查异常值，并对受影响的整个 batch 重算，最多重试 3 次。对于独立重放未再复现的异常，这属于运行时绕行措施，不能作为算法稳定性的证据。创建 LIBERO 的 CPU 仿真子进程前，适配还会清空 MUSA 设备可见性，避免不必要的设备上下文加剧初始化竞态。

减少世界模型搬运并保持数值一致
------------------------------

显存可控后，频繁的 host 与设备间搬运成为性能优化的重点。输入图像经过 PIL 和 NumPy，VAE 输出又逐帧回到 host。实验通过 ``WOVR_FAST_IO`` 开关集中启用以下改动：

- 将输入条件帧保留在设备上，去掉逐帧 PIL 往返。
- 将去噪过程中每轮多次同步的有限值检查合并为整次去噪结束后检查一次，保留 NaN/Inf 重试。
- 将 DiffSynth 高频执行路径中的 Python 标量转换为零维设备 tensor。

视频帧会量化回 ``uint8`` 并反馈给后续预测，即使只有 1 ULP 的差异，也可能在反馈中放大。因此，仅保证误差很小还不够。为复现原始 NumPy 归一化结果，适配在 host 上预计算 256 项 ``uint8`` 到 ``[-1, 1]`` 的查找表，设备端只做索引。报告中的逐位检查在 A100 和 S5000 上均比较了 2044 万个元素，差异为 0。

在这组 8 卡对照中，env 交互耗时约从 2050 s 降至 975 s；完整训练整步耗时从关闭性能开关时的约 3100 s，降至开启后的约 1900 s。这些优化在保持训练计算语义的前提下调整数据搬运与同步路径，与下面的配置 A/B 属于不同实验。

单机精度与性能验证
------------------

逐位检查覆盖的是特定数值变换，训练后的 policy 还需要独立评测；性能配置也需要在同一台机器、同一份数据上对照。

训练曲线与仿真器评测
~~~~~~~~~~~~~~~~~~~~

报告中，两种硬件的 191 步训练成功率曲线相关系数为 0.976。最终 policy 效果由 LIBERO 仿真器评测，与世界模型内部预测的奖励分开统计。

   :header-rows: 1
   :widths: 40 30 30

   * - 评测时间点
     - S5000
     - A100
   * - RL 训练前
     - 55.0%
     - 59.7%
   * - 第 190 步
     - 74.6%

报告中的差异检验为 ``p = 0.76``，在这次实验窗口内没有统计显著性。仅凭这一结果，还不能证明其他配置或多次训练下的效果等价。

8 卡配置 A/B
~~~~~~~~~~~~

实验的 ``perfA`` 配置使用 ``actor.micro_batch_size: 32``、``actor.global_batch_size: 8192`` 和 ``actor.fsdp_config.enable_gradient_accumulation: False``。原文将最后一项列为相对 ``wan_spatial_official_s5000.yaml`` 可追溯的配置差异。这些设置用于说明报告中的实验，不能据此反推未保留的历史配置。

在 FSDP1 中，该开关控制中间 micro batch 是否通过 ``no_sync()`` 暂缓梯度同步。设置为 ``False`` 后，每个 micro batch 都可以同步梯度，全局 batch 大小仍由配置指定。以下结果来自同一台 8 卡机器、同一份数据，取 3 步平均。

   :widths: 34 22 22 22

   * - 指标
     - 基线
     - perfA
     - 变化
   * - 整步耗时
     - 2110.7 s
     - 1887.6 s
     - −10.6%
   * - actor / GRPO 训练

耗时下降集中在 actor 训练阶段，与 micro-step 开销减少一致；世界模型生成仍占整步约一半。这是可通过开关回退的配置实验，不能据此建议所有模型或网络都采用相同的梯度同步设置。

扩展到双机 16 卡
----------------

从单机扩展到两台 8 卡机器后，初始化与网络带来额外约束。16 个进程同时首次访问 MUSA，可能触发驱动惰性初始化竞态，表现为没有日志的挂起。RDMA userspace 组件缺失时，MCCL 还可能回落到 Socket，使网络配置问题看起来像训练停滞。

实验中的 ``WOVR_DEV_INIT_STAGGER=3`` 按 rank 错峰初始化；``WOVR_FSDP_SHARD_SIZE=8`` 创建以节点数和每节点卡数为两个维度的设备 mesh。混合分片在机内完成参数 all-gather，跨机通信承担必要的梯度归约。FSDP1 计算梯度范数时，也需要在机内分片组中归约。

.. list-table:: 双机 16 卡分片对照
   :header-rows: 1
   :widths: 34 22 22 22

   * - 指标
     - full-shard
     - hybrid-shard
     - 变化
   * - 整步耗时
     - 824.8 s
     - 698.6 s
     - −15.3%
   * - 权重同步
     - 278.9 s
     - 93.7 s
     - 约 −66%

将大块参数聚合保留在机内，减轻了约 4.7 GB/s 跨机链路的压力。错峰初始化、容器进程数上限、RDMA 与网络配置，以及干净的 Ray 任务状态，都属于这次运行的启动条件。双机数据与 8 卡实验来自不同配置和测量窗口，不能用两张表直接计算从 8 卡到 16 卡的扩展效率。

仍需验证的边界
--------------

本次适配跑通了训练闭环，并分别测量了 policy 效果、单机整步耗时和双机通信性能。复现时，应保留这三类对照各自的实验条件。断点续训和部分驱动初始化场景仍需独立验证，NaN 重试与 CPU 中转权重同步也仍是实验实现中的平台绕行措施。

后续优化应继续减少世界模型生成开销，并在驱动与通信库修复后重新评估设备直传。当前维护的训练流程见 :doc:`Wan 示例 <../../examples/embodied/wan>`；方法背景见 :doc:`WoVR 论文介绍 <../publications/wovr>` 和 `WoVR 论文 <https://arxiv.org/abs/2602.13977>`_。
