从算力到吞吐：RLinf 具身模型的 Ascend 优化设计
==============================================

RLinf 通过复用 attention 控制信息、重叠分片参数通信，以及重新组织动作生成中的主机与设备工作，提高具身模型在 Ascend 上的完整调用吞吐。这些设计面向一个共同问题：加速卡已经具备较高的矩阵计算能力，模型却仍在等待输入准备、控制信息和下一层参数。理解这些等待如何进入关键路径，才能判断一项优化为何有效、适用于哪些模型，以及在什么条件下会失效。

具身模型的一次预测通常包含图像预处理、视觉与语言特征提取，以及动作生成。采用多步去噪的模型，还会反复执行动作网络。强化学习训练又增加了 logprob 重计算、反向传播和分片参数通信。因此，矩阵算子的速度、完整动作调用的速度和一轮强化学习训练的速度是三个不同层次的指标。下面从完整调用的数据流出发，解释几类主要设计，再用匹配输入下的测量说明其收益。

从矩阵算力到完整模型调用
------------------------

完整调用的优化首先需要明确设备在等什么。在本次四卡服务器测试中，Ascend 910B3 的 8192 × 8192 BF16 稠密矩阵乘法（GEMM）为 272.8 TFLOPS，A100-SXM4-80GB 为 293.2 TFLOPS，相对性能为 93.04%。但显存 copy 的相对带宽为 72.24%，四卡 all-gather 的相对 bus bandwidth 为 30.06%。主机侧也有差异：同一组 Python 循环测试中，Kunpeng-920 的耗时为 193.0 ms，Xeon Platinum 8358 为 98.0 ms。这些数字说明，提升矩阵利用率只是优化的一部分，通信和主机依赖同样可能决定设备何时开始下一段计算。

.. figure:: https://raw.githubusercontent.com/RLinf/misc/0eb11a375a8a73130527211d079d6c21ccca8c7f/pic/ascend_opt/call_critical_path_zh.png
   :alt: 动作推理、bootstrap 与训练的计算依赖示意
   :align: center

   模型调用跨越主机与设备。箭头表示数据依赖，图中没有按比例表示耗时；训练中的参数通信还会与前后向计算产生依赖。

以一次动作调用为例，CPU 先整理图像和文本，设备随后计算视觉与语言特征，动作头再根据这些特征生成控制量。若 CPU 必须读取设备 tensor 中的一个整数，后续工作就需要等这个整数可用。整数本身只有几个字节，但它前面的设备计算可能还未结束，等待成本取决于依赖链，而不取决于整数大小。对一个短算子反复同步，可能比算子本身更昂贵。

bootstrap 的消费方则需要下一观测的 value，用它估计后续回报。对于带 value head 的 OpenVLA，这条路径可以使用 prompt 的 hidden state，不必完成动作 token 的自回归解码。因而动作调用与 bootstrap 的计算量必须分别统计。训练进一步包含反向和 FSDP 通信，单次 forward 的加速比例也不能直接套用到训练。

这三个执行阶段形成了后续设计的边界：控制信息应按真实有效期复用，必要计算应按依赖关系重叠，而任务不消费的结果可以在确认调用契约后缩减。每一项改动都需要回到完整接口测量，确认局部节省真正缩短了关键路径。

把 attention 的控制信息移出逐层关键路径
---------------------------------------

attention 的第一项优化来自输入组织方式，而不是更换 Q/K/V 的计算。一个 batch 中的文本长度可能不同，视觉 token 数量也可能随图像网格变化。模型除了计算特征，还需要知道有效 token 的位置、每条序列的边界，以及哪些位置允许互相读取。这些长度、索引和 mask 是控制信息；在同一次调用中，它们往往会被几十层网络重复使用。

attention 用 query（Q）与 key（K）计算位置之间的匹配分数，再根据归一化后的权重汇总 value（V）。Q/K/V 是每层根据特征产生的计算数据，长度与 mask 则决定这些数据如何组织、哪些位置可以交互。两者的变化频率不同，元数据复用正是利用了这一区别。

从序列边界到主机同步
~~~~~~~~~~~~~~~~~~~~

.. figure:: https://raw.githubusercontent.com/RLinf/misc/0eb11a375a8a73130527211d079d6c21ccca8c7f/pic/ascend_opt/metadata_lifetime_zh.png
   :alt: attention 控制信息的版本校验、缓存复用和重新计算边界
   :align: center

   元数据缓存与调用内网格复用采用不同有效期，各层始终使用当前特征计算输出。

假设两个样本的有效长度分别为 5 和 3。去掉 padding 后，两条序列可以连续存放，累积边界为 ``[0, 5, 8]``。当前已检查的旧版 Transformers NPU FlashAttention 路径需要以 CPU tuple ``(5, 8)`` 表示序列终点。设备上保存的边界必须先传回主机，才能构造这个 tuple。若每层都重新转换，同一份控制信息就会反复成为设备计算与主机下发之间的同步点。

``rlinf/models/embodiment/gr00t/npu_common.py`` 中的 ``install_npu_flash_attention_cache`` 在已经识别的旧版 NPU 接口上复用三类对象：去 padding 的索引与长度、累积长度对应的 CPU 终点，以及同一设备上的 causal mask。第一层按原路径生成这些对象，后续层在输入仍有效时复用。每一层的 Q/K/V、attention 输出和梯度仍由当前层重新计算。

这里需要区分两类有效期。padding 和序列边界属于当前输入，其缓存必须随输入变化而失效；固定大小的 causal mask 只描述位置之间的先后关系，可以按设备复用。把两者都做成一个“按 shape 缓存”的字典会掩盖这个区别：相同 shape 的两个 padding mask 完全可能描述不同的有效位置。

缓存的正确性取决于失效规则
~~~~~~~~~~~~~~~~~~~~~~~~~~

复用前，实现核对 tensor 对象及其版本。普通 PyTorch tensor 在原位写入后会更新版本计数，因此同一个对象发生内容变化时，缓存仍会重新计算。缓存保留 weak reference，用于确认对象确实还存在，也避免仅凭重复使用的 Python 对象地址误认输入。条目数量受限，以约束长时间运行中的保留状态。

inference tensor 不具备相同的版本跟踪条件，graph capture 还要求计算使用本次写入的动态内容，这两类调用因此走重新计算的路径。这是一项有意保留的边界：当实现无法证明缓存仍然有效时，继续使用原转换过程。缓存命中率必须服从输入语义，而不能反过来要求调用者保持隐含条件。

相同原则也适用于视觉网格。``grid_thw`` 描述时间、高度和宽度方向的 patch 数量；例如 ``[1, 3, 2]`` 表示单帧图像的 3 × 2 网格。位置编码和窗口索引会读取同一组整数。已测原型在一次视觉 forward 内集中生成 CPU 描述，两个消费方共用这份描述，并在调用退出时清理。下一次图像即使网格相同，视觉特征仍需根据新的像素计算；网格复用不能变成图像结果复用。

这种调用内设计也使清理边界更直接：一次视觉 forward 进入时保存设备网格与 CPU 副本，位置处理方法确认收到的是本次网格后使用副本，退出时通过 ``finally`` 恢复原作用域。已测推理与训练原型分别应用于经过检查的视觉路径；推理原型限定单帧图像，其他时间维度仍需遵循原位置编码规则。

StarVLA 在 B32 下的完整动作调用由 0.764 s 降至 0.654 s，吞吐提升 16.96%；GR00T N1.7 的相同 batch 对照提升 10.83%。StarVLA 在 M16、已启用 FSDP 预取的基线上增加位置与网格处理后，每 rank 的训练调用吞吐提升 8.28%–29.52%。前两项为网格处理的单项对照，后一项同时包含位置与网格处理，不能全部归因于一次 CPU 副本。

mask 转换需要保留数值含义
~~~~~~~~~~~~~~~~~~~~~~~~~

OpenVLA 的另一条路径通过 PyTorch SDPA 调用 attention。浮点 mask 会加到 attention logits 上，布尔 mask 则表示哪些位置参与 attention。在已测 torch-npu 版本中，符合条件的布尔 mask 可以走融合 kernel；浮点表示可能使执行落入分解路径。因此，``rlinf/scheduler/hardware/accelerators/ascend_npu.py`` 在 NPU worker 初始化时安装转换 wrapper。

转换并不等于对浮点 mask 求真假。允许的位置必须恰好为 0，屏蔽位置必须符合已检查的极小负数条件。一个 ``+0.2`` 的值是在改变某个位置的 attention 分数，一个 ``-0.2`` 的值也在改变相对权重，它们都不能变成简单的允许或屏蔽。如果 mask 需要梯度，转换还会改变其可微性，所以继续保留浮点路径。

整行屏蔽尤其容易被忽略。若某一行所有位置都加上同一个有限负数，softmax 的相对分数仍可能形成非零分布；全 ``False`` 的布尔行则有不同输出语义。实现会单独检查整行条件，只在转换可以保留当前路径含义时使用布尔表示。判定结果按 tensor 版本缓存，后续层复用；一旦输入修改，就重新检查。

设计边界与实测收益
~~~~~~~~~~~~~~~~~~

GR00T N1.5/N1.6 的结果来自相同 batch 下的缓存开关对照。GR00T N1.6 的 B16 完整动作调用从 4.249 s 降至 1.122 s，样本吞吐提升 278.62%；GR00T N1.5 从 1.067 s 降至 0.361 s，提升 195.52%。四卡训练调用的提升分别为 37.01%–39.04% 和 41.76%–42.32%。这些变化说明，原路径中重复准备控制信息的成本已经足以主导相当一部分完整调用时间。

OpenVLA 的对照基线已经包含原有 mask 缓存。已测 view 复用原型还核对 storage、shape、stride、offset、dtype、device 和版本，再决定是否复用同一底层数据的判定结果；这比仓库中的 tensor 对象级缓存具有更具体的布局约束。加入该原型后，B64 动作调用的提升为 3.51%，bootstrap 为 1.15%。相同的设计原则可以消除重复工作，但它的收益取决于原调用里还有多少可消除的重复。GR00T 的大幅提升不能直接作为 OpenVLA 或其他 Transformers 版本的预期收益。

让分片参数的通信与计算重叠
--------------------------

移除重复控制开销后，训练中的下一项主要等待来自参数通信。FSDP（Fully Sharded Data Parallel）将参数、梯度和 optimizer 状态分布在多个 rank 上，以降低单卡常驻显存。这里的每个 rank 是负责一张卡的训练进程。某个分片模块开始计算前，需要先通过 all-gather 组成完整参数。若等到当前层计算结束才为下一层发起通信，两段工作就会串行出现在关键路径上。

预取改变的是通信发起时间
~~~~~~~~~~~~~~~~~~~~~~~~

.. figure:: https://raw.githubusercontent.com/RLinf/misc/0eb11a375a8a73130527211d079d6c21ccca8c7f/pic/ascend_opt/fsdp_overlap_zh.png
   :alt: FSDP 按需通信与参数预取的依赖时间线
   :align: center

   预取将下一层 all-gather 提前到当前层计算期间。该图只说明依赖关系与重叠方式，矩形宽度不是实测耗时。

参数预取在当前层计算期间发起下一层的 all-gather，让设备计算与通信并行推进。若当前层计算时间为 ``C``，下一层参数传输时间为 ``G``，串行安排需要经历约 ``C + G``，理想重叠后的这一段约为 ``max(C, G)``。这只描述相邻计算与通信的依赖关系，实际训练还包含第一层准备、最后一段收尾、反向计算、资源竞争和其他同步。

这也解释了预取的收益上限：它不会提高互联的物理带宽，也不会减少必须传输的参数字节数。当 ``G`` 明显大于 ``C`` 时，仍会留下无法覆盖的通信等待；当通信与计算争用设备资源时，重叠后的两项工作也可能比单独执行更慢。是否有效必须在实际 FSDP 包装粒度和多卡拓扑下测量。

OpenVLA-OFT 的已测配置沿用 RLinf 现有选项：

.. code-block:: yaml

   actor:
     fsdp_config:
       forward_prefetch: true
       backward_prefetch: pre
       limit_all_gathers: true

``forward_prefetch`` 提前准备前向所需的参数，``backward_prefetch: pre`` 提前发起后续反向计算所需的通信。参数提前到达意味着多个模块的完整参数可能同时驻留，``limit_all_gathers`` 用于约束在途 all-gather，控制显存压力。预取深度、模块包装粒度和显存预算因此需要一起考虑。

batch 同时影响重叠机会与训练含义
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

增加单个 rank 的 micro batch，通常会增加每次前后向的计算工作量；对于参数量不变的模块，参数 all-gather 的规模并不会按样本数同比增加。这可能创造更长的通信覆盖窗口，也能摊薄固定下发成本。但更大的 micro batch 会占用更多激活显存，可能挤占预取所需空间。因此，batch 与预取不是相互独立的两个开关。

global batch 还有另一层含义：它决定一次 optimizer 更新使用的总样本数。若将每 rank 的 micro batch 从 16 改为 32，同时将四卡 global batch 从 64 改为 128，参数更新频率与所见样本之间的关系也随之变化。吞吐实验可以比较每秒处理的样本数，学习实验则必须继续检验相应配置的训练效果。二者分别回答计算是否更高效、优化后的训练是否仍然有效。

训练 batch 的独立对照使用样本吞吐 ``batch / 耗时`` 判断收益。π₀ 从 M16/G64 调整为 M32/G128 后，每 rank 耗时由约 0.86 s 增至 1.32 s，样本数翻倍而耗时未翻倍，因此样本吞吐提升 29.67%–31.08%。π₀.₅ 和 Dexbotic-π₀ 的相应提升为 27.62%–28.08% 和 14.57%–14.72%。这些对照改变了 global batch，结果不能直接解释为相同更新轨迹上的加速。

在相同 M8/G32 下，OpenVLA-OFT 增加前后向预取后，每 rank 的训练调用吞吐提升 39.90%–40.76%。StarVLA 的相同 M16/G64 对照中，提升为 186.25%–240.03%。这里的训练调用覆盖前向、loss、反向及调用内通信，计时不包含 optimizer；StarVLA 使用调用外恢复固定 checkpoint 的方式保持有效梯度。它们是对应配置下的调用收益，不能直接当成完整强化学习迭代的加速倍数。

GR00T N1.6/N1.7 的最终训练组合也启用了预取，现有实验没有单独分离其贡献。比较这些模型时，应保留组合结果的归因范围，而不是把另一模型的预取收益移植过来。

缩短多步动作生成中的主机间隙
----------------------------

通信重叠处理了设备之间的等待，动作生成还需要处理主机与设备之间的细粒度依赖。π₀、π₀.₅ 和 Evo-1 一类模型通过多步去噪逐渐生成动作：当前动作 tensor 随步骤更新，而观测上下文、预先确定的 timestep 和部分分支选择在一次采样内保持稳定。这些量的变化频率不同，适合采用不同的执行方式。

预先确定的控制量只读取一次
~~~~~~~~~~~~~~~~~~~~~~~~~~

当去噪循环已经在主机侧确定调度表或随机步骤索引时，在循环内通过 ``.item()`` 从设备 tensor 逐步读回控制标量会引入不必要的同步。``rlinf/models/embodiment/evo1/evo1_rl_head.py`` 中的 ``rl_denoise_sample`` 先在主机上抽取一次 ``selected_step``，同时把训练回放所需的 ``denoise_inds`` 写入设备，而循环内的分支直接读取主机整数：

.. code-block:: python

   selected_step: int | None = None
   if mode == "train" and not joint_logprob:
       selected_step = random.randint(0, last_step)
   for idx in range(N):
       step_mode = (
           "train"
           if mode == "train" and (joint_logprob or idx == selected_step)
           else "eval"
       )

被选中的步骤与随机数调用顺序保持不变，只是消除了循环内的设备到主机往返。若用不同 dtype 或运算顺序另算一组控制量，可能改变后续数值；依赖当前网络输出才能确定的控制量，则无法提前搬到循环外。

同一原则也适用于 π₀ 与 π₀.₅ rollout 中预先确定的 timestep 序列：在主机侧保留调度表即可避免逐步标量同步，同时保持传入网络的 tensor 数值不变。随机调用的次数与顺序保持原流程；噪声生成和完整去噪轨迹仍参与后续 logprob 回放。

主机执行条件会放大或抵消这类节省。增加 CPU 线程数可能加速大型预处理，也可能增加小算子的线程协调成本。本次 π₀/π₀.₅ 对照同时采用了 8 个 CPU 线程，因此 64.48% 和 8.78% 的完整动作吞吐提升分别属于各自的组合配置，无法再拆成控制量处理与线程数的独立收益。

多路 CPU 通常将核心与内存划分为多个 NUMA 节点，线程访问邻近内存与设备的成本可能低于跨节点访问。NUMA 亲和性处理的就是这类主机成本：把负责某张 NPU 的进程线程安排在拓扑相邻的 CPU 节点，降低跨节点访问和迁移带来的不稳定性。ABot-M0 相同训练配置下，每 rank 的调用吞吐提升为 5.61%–6.66%。该实验只约束 CPU 亲和性，没有显式绑定内存分配节点；部署到另一台机器时，需要重新读取设备与 NUMA 拓扑，不能复用固定 CPU 编号。

让稳定的计算区域一次下发
~~~~~~~~~~~~~~~~~~~~~~~~

控制量的同步移出循环后，设备仍可能因逐个下发小算子而出现间隙。执行图把一组算子及其依赖捕获下来，随后通过一次 replay 执行这组工作。适合捕获的区域需要具有稳定输入结构和明确的存储生命周期，例如语言 MLP 或动作头的确定性网络部分。采样噪声和需要主机参与的动态逻辑保留在图外。

.. figure:: https://raw.githubusercontent.com/RLinf/misc/0eb11a375a8a73130527211d079d6c21ccca8c7f/pic/ascend_opt/graph_replay_ownership_zh.png
   :alt: 执行图静态输入、参数存储与输出所有权
   :align: center

   replay 复用运算安排，每次仍读取本次输入。输入缓冲区保持地址稳定，输出复制后交给调用方；参数存储迁移需要调用层先释放旧图。

``rlinf/utils/cuda_graph.py`` 的 ``CUDAGraphManager`` 为 CUDA 与 NPU 提供捕获、输入更新、重放和释放接口。``graph_signature`` 区分输入的 shape、dtype、具体 device，以及 list、tuple、mapping 和标量类型。这个签名描述执行条件，不描述图像或 hidden states 的具体内容；内容由每次 replay 前的输入复制更新。

捕获得到的 ``GraphSpec`` 持有图对象、静态输入和静态输出。静态缓冲区也规定了输出的所有权。一次 replay 的输出通常落在图捕获时确定的存储中，下次 replay 会覆盖同一块存储。异步 channel 可能仍在发送上一次结果，调用方也可能在后续步骤继续读取它。因此，模型 wrapper 在返回前复制输出，让图管理器和调用方各自拥有自己的结果：

.. code-block:: python

   copy_tensor_tree(graph.inputs, current_inputs)
   graph.graph.replay()
   owned_outputs = clone_tensor_tree(graph.outputs)

``copy_tensor_tree`` 校验输入 shape、dtype 和静态元数据，原位更新已捕获缓冲区。``clone_tensor_tree`` 则为 tensor 输出创建独立存储。完整调用的计时必须包含这些复制；只测 replay 本身，会遗漏维持接口正确性所需的成本。

参数也有存储条件。optimizer 在原存储上更新参数时，replay 可以读取新值；offload、替换模块或重新分配参数存储则可能使旧图引用失效。这个生命周期由模型调用层负责：在移动权重前释放图，需要时重新捕获。已测语言 MLP 原型还显式核对参数 storage，发现变化后回到 eager 路径。图管理器本身没有替调用者推断模型生命周期。

在 NPU 上，当前图后端不提供 CUDA generator registration 对应的接口，因此这里将随机采样保留在捕获区域之外。这样既能减少确定性网络部分的下发成本，也能继续沿用原采样顺序与 RNG 状态。把更大范围强行纳入图中并不必然带来更高收益，反而可能扩大动态输入、随机状态和显存管理的约束。

GR00T N1.6 和 ABot-M0 的语言 MLP 图重放对照分别得到 4.24% 和 1.40% 的完整动作吞吐提升，已包含输入输出复制。其基线已采用相应的位置处理和动作头配置。这些结果反映了 Amdahl 定律的约束：若下发开销只占完整调用的一小部分，即使把这一部分大幅缩短，整个模型也只会获得有限提升。Evo-1 的动作头也提供可选图路径，但现有独立测量不足以赋予它同一项收益。

根据下游需求确定计算范围
------------------------

消除等待后，还需要判断哪些计算会被当前任务实际消费。控制信息复用和参数预取主要改变工作安排，这一类优化则可能直接减少执行的 FLOPs。因此，样本吞吐与 TFLOPS 需要分别解释：处理同样样本更快，并不要求每秒执行的浮点运算量也按相同比例上升。

保留特征，缩减未使用的词表输出
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

语言模型先为每个 token 生成 hidden states，再通过词表投影得到 logits。设 batch 为 B、序列长度为 L、hidden size 为 D、词表大小为 V，完整词表投影的主要矩阵计算量约为 ``2BLDV``，输出 shape 为 ``[B, L, V]``。如果动作头读取 ``[B, L, D]`` 的完整特征，却不读取完整 logits，这个投影就超出了当前任务的消费范围。

GR00T N1.5 的已测动作训练原型在确认没有语言 labels、且返回完整 hidden states 的前提下，使用语言模型已有的 ``logits_to_keep=1``。动作头仍得到全部序列特征，词表投影只处理一个位置，主要计算量缩为 ``2BDV``。这里缩减的是特征之后的投影，不能把特征序列本身一起截短。

同一 M128/G512 配置下，该设计使每 rank 的训练调用吞吐提升 9.34%–9.50%。FLOPs 统计也随实际执行范围重新计算；若继续使用完整词表投影的运算量作分子，就会虚增优化后的 TFLOPS。存在语言 labels、需要完整词表分数或其他下游消费者的调用，则仍需保留完整路径。

bootstrap 直接请求所需的 value
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

OpenVLA 的 bootstrap 也可以根据消费方需求缩减计算。带 value head 的模型使用 prompt 最后一个位置的 hidden state；第一个动作 token 生成前，这个特征已经可用。``predict_value_batch(env_obs)`` 沿用动作调用的图像与 prompt 预处理，完成一次特征提取后返回 shape 为 ``[B, 1]`` 的 value。

HuggingFace rollout worker 通过两个独立选项控制请求组织与计算范围：

.. code-block:: yaml

   rollout:
     batch_bootstrap_inference: true
     value_only_bootstrap: true

第一个选项把当前收到、需要终止 value 的多个请求合并成一个 batch，再按原请求大小拆回结果。终止观测来自上一 episode，环境 reset 后的初始观测属于下一 episode，两者不能混用。合并后仍要保留每个结果对应的轨迹归属，不能只得到一个顺序不明的 value tensor。

第二个选项要求 ``model_type: openvla``，并在存在 value head、适用的算法路径下直接请求 value。RLT、DAgger 和未配置 value head 的模型继续采用原路径。两个选项默认均关闭，可以分别验证其效果。

缩减无用动作生成也会少消耗随机数，所以相同 seed 下后续动作序列可能变化。这与“本次 value 是否一致”是两个不同问题。接口数值对照需要检查 value，训练验证还需观察完整学习过程；不能因为省去的动作没有发送给环境，就推断其随机状态影响也不存在。这里不为两个选项附加未经独立量化的提升比例。

在一次采样内复用不变的上下文投影
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Evo-1 的多步去噪中，动作 query 随步骤变化，但同一次调用的图像与文本上下文保持不变。对于使用该上下文的 cross-attention block，有 ``K = X_context W_K``、``V = X_context W_V``。在上下文和参数均不变时，这两项线性投影也不变，可以在首次使用时计算，后续步骤复用；当前动作的 Q 和 attention 仍在每步重新计算。

已测原生算子方案将复用范围限定在 eval、关闭梯度的单次动作采样内。新观测进入下一次调用后重新计算投影；需要训练梯度的路径继续遵循原图构建方式。这个边界避免跨观测复用过期特征，也避免把一次采样的 detached 结果误用于训练。

这与 attention 长度、mask 缓存具有不同含义：后者复用输入组织方式，K/V 复用则复用满足不变条件的实际中间特征。两者都需要明确有效期，但不能共用一套仅按 shape 判断的缓存规则。Evo-1 当前结果包含这项设计，缺少独立开关对照，因此只报告整体方案的性能。

按 batch 组织输入，同时保留预处理语义
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

输入准备同样可以减少重复工作。逐帧构造对象、归一化和传输会重复支付 Python 调度与小块拷贝的固定成本。对 shape 一致的图像，先组批再传输和处理，可以让一次设备调用覆盖更多输入。OpenVLA/OFT、StarVLA、GR00T、Evo-1 和 Dexbotic 路径根据各自 processor 的要求采用相应组织方式，不能用一份通用 resize 替换所有模型。

预处理直接定义模型看到的输入。center crop 与 resize 的顺序、插值方式、padding 颜色、浮点图像的范围和 uint8 转换前的 clipping 都可能改变像素。图像已经具有目标尺寸，也不意味着可以跳过原有 crop。设备组批路径因此需要与原 processor 对照普通输入和边界输入；无法保持当前语义的格式继续使用原路径。

实际 dtype 也必须在参数、投影输入和连续状态之间保持一致。Dexbotic 模型工厂将配置的 ``torch_dtype`` 传入加载路径，连续状态在投影边界与参数 dtype 对齐；未指定 precision 时保留原加载行为。比较双平台吞吐时，应核对实际参数与输入 dtype，而不能只根据 YAML 中写了 BF16 就认定执行精度已经匹配。

GR00T N1.6 的独立原型保留原 collator 的 resize 与文本流程，仅集中传输符合条件的图像并通过原 image processor 批量归一化。在 B16、8 个 CPU 线程下，完整动作调用由 0.609 s 降至 0.586 s，吞吐提升 3.95%。该原型尚未正式接入，其余上述输入路径没有可在此单独归因的完整调用收益。它们是否值得启用，取决于原 processor 的主机成本、输入 batch 和设备传输条件，也需要计入新增暂存 buffer 的显存开销。

用可复核的测量说明收益
----------------------

上述设计分别改变控制信息的有效期、必要工作的调度方式和实际计算范围。要解释最终结果，需要先保证比较对象相同，再说明收益属于哪个范围。大矩阵基准、局部 kernel 对照、完整模型调用和完整强化学习训练，各自只能支撑对应层次的结论。

固定输入下比较动作、bootstrap 和四卡训练
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

性能对照中，Ascend 侧使用 PyTorch 2.6.0+cpu、torch_npu 2.6.0 与 CANN 9.1.1，A100 侧使用 PyTorch 2.11.0+cu128 与 CUDA 12.8。各模型采用独立环境，双平台匹配 checkpoint、配置、实际 dtype 和输入 shape；底层软件版本差异属于本次系统比较的条件。

推理重放已保存的真实观测，核对双平台预处理后的像素、token、mask 和序列长度。计时覆盖完整预测接口的主机处理、设备计算及解码，预热 5 次后测量 20 次，以同步后的耗时中位数计算吞吐。大 batch 来自固定观测组批，说明模型接口的计算容量；环境系统能同时运行多少实例需要另外验证。

训练使用四个真实 actor rank 各自保存的 micro batch，执行前向、loss、反向、FSDP 通信和 optimizer 更新。TFLOPS 的计时覆盖前向、loss、反向及调用内通信，不包含 optimizer；每 rank 测量 25 次，前 5 次预热。四个 rank 的输入分别配对，训练比值取各 rank 结果的范围，不能用最快 rank 代表四卡整体训练效率。

FLOPs 按匹配输入下的实际路径独立统计，包括反向和重计算，并对自定义 attention 根据实际序列长度与 head 结构校准。计算方式为 ``TFLOPS = 实际 FLOPs / 调用耗时 / 10¹²``。当优化减少词表投影或冻结模块的反向图时，分子随实际计算变化；当优化只消除等待时，分子保持相同。

验证需要覆盖输出、状态与生命周期
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

一次动作输出一致，还不足以说明优化可以进入训练。验证范围包括 rollout 动作与 logprob、保存的回放输入、训练梯度，以及实际 optimizer 更新后的参数和状态。对于复用与 graph 路径，还要改变输入、原位更新权重、切换 batch、移动或重新加载模型，并检查释放后能否再次使用。缓存可能只在第二次调用或更新权重后出错，这些情形需要由真实生命周期触发。

随机状态也属于执行结果的一部分。相同输入下比较 Python、CPU 和设备 RNG 状态，可以识别随机调用顺序被改变的设计。对于明确省去随机动作生成的 value-only bootstrap，需要说明这种变化并单独检查学习效果，而不是要求所有优化都满足同一个不适用的 bitwise 条件。

最后，固定 micro batch 的正确更新证明了训练路径可执行，完整学习曲线回答的是持续训练是否仍有效。恢复运行时，需要核对模型、optimizer、学习率 scheduler 及各 rank 的 RNG；模拟器与 rollout 状态若重新初始化，也必须在实验条件中说明。训练成功率来自实际 rollout，不能等同于独立评测集上的泛化成功率。最终结果应同时给出完整调用性能和相应学习证据，让读者知道每项结论的适用范围。

持续训练是否形成学习进展
~~~~~~~~~~~~~~~~~~~~~~~~

数值对照检查一次更新是否保持预期行为，持续训练则观察这些更新能否累积为学习进展。我们以 OpenVLA-OFT 为例，在 A100 和 Ascend 910B3 上从相同初始 checkpoint 出发，采用同一 LIBERO-10 GRPO 协议分别完成 45 个 epoch。两端实验均于 2026 年 10 月 17 日前完成。

每个平台使用四张卡和 32 个训练环境，采用 BF16，micro batch 为 16，global batch 为 8192；每个 epoch 包含 16 轮 rollout 和 4 次 optimizer 更新。环境 seed 为 0，actor seed 为 1234，训练采样 temperature 为 1.6，模型不带 value head。这组配置服务于持续训练验证，与前面的固定输入性能测量具有不同的 batch 和目的。

本实验保持原 GRPO 配置，两端均关闭 FSDP 的 ``forward_prefetch`` 和 ``backward_prefetch``，``limit_all_gathers`` 为 ``False``。本节曲线对应这一配置下的持续训练表现；预取配置的梯度和 optimizer 更新正确性由匹配输入的四卡数值对照验证。

两端均记录了完整的 45 轮成功率与有限、非零的梯度 norm，并正常退出。最终四卡 checkpoint 的各分片完整性、optimizer 状态与进度、scheduler 进度和各 rank 的 RNG 状态均已核验：optimizer 累计更新 180 次，scheduler 进度为 45。训练 rollout 的 ``env/success_once`` 表示 episode 内至少成功一次的比例，下表直接由原始记录计算。
