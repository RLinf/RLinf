SO101 Setup and Control
=======================

This page shows you how to set up an SO101 follower and leader, check both arms,
and collect joint-space demonstrations with a repeatable episode reset.

.. figure:: https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/lerobot/SO101_Follower.webp
   :align: center
   :width: 70%

   SO-101 follower with its gripper. Image: Hugging Face LeRobot.

Overview
--------

Hardware checks and demonstration collection run on the Linux machine connected
to the arms. They require no GPU or model checkpoint. Start with the follower,
add the leader after both arms are calibrated, then use the collection config to
record episodes with the same joint and gripper reset state.

Hardware Setup
--------------

Prepare the arm and controller machine before installing the software.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Component
     - Requirement
   * - Follower
     - SO-101 arm with its gripper, servo controller, and the power supply specified for the kit.
   * - Controller machine
     - Linux computer with a USB connection to the follower's servo controller.

For an unassembled arm, follow the parts and assembly instructions in the
`LeRobot SO-101 guide <https://huggingface.co/docs/lerobot/so101>`_. Configure new
motors individually before completing the wiring; the installation steps below
include the required commands.

Installation
------------

Install the robot dependencies on the controller machine using the custom-environment
workflow below. Run the checks from the same checkout and activated environment.

Robot Controller Node
~~~~~~~~~~~~~~~~~~~~~

Clone RLinf on the machine connected to the robot, then install its environment.

.. include:: _setup_common.rst
   :end-before: Then set up the dependencies

Install the robot dependencies from the repository root:

.. code-block:: bash

   # Mainland China users can add --use-mirror for faster downloads.
   bash requirements/install.sh embodied --env so101
   source .venv/bin/activate
   export REPO_PATH="$PWD"

The installer includes LeRobot with Feetech support. Run subsequent commands
from this checkout with the environment activated. See
:doc:`Installation </rst_source/start/installation>` for platform prerequisites.

Find the Port and Configure the Motors
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Connect the servo controller's USB cable and the power supply specified for
your kit. Find which serial device belongs to the follower:

.. code-block:: bash

   lerobot-find-port

Unplug the USB cable when prompted, then reconnect it. The reported device path
is the port to use below; these examples assume ``/dev/ttyACM0``. Check access:

.. code-block:: bash

   ls -l /dev/ttyACM0
   id -nG

On Ubuntu, a port owned by the ``dialout`` group requires your account to belong
to that group. If it does not, run ``sudo usermod -aG dialout "$USER"``, log out
and back in, then return to the checkout and reactivate ``.venv``. Recheck the
port path after reconnecting USB.

For new or replaced motors, assign IDs and baud rates once, following the
upstream guide's wiring sequence:

.. code-block:: bash

   lerobot-setup-motors \
     --robot.type=so101_follower \
     --robot.port=/dev/ttyACM0

Connect only the motor named by each prompt to the controller. The tool assigns
its ID and baud rate before requesting the next motor. After all six motors
are configured, complete the assembly and reconnect the daisy chain as shown
in the guide. Skip motor setup for an already configured arm; calibration is
still needed under the ID you will use with RLinf.

Calibrate the Follower
^^^^^^^^^^^^^^^^^^^^^^

With the motors configured and the arm assembled, calibrate the follower from
a terminal before RLinf opens the serial bus:

.. code-block:: bash

   lerobot-calibrate \
     --robot.type=so101_follower \
     --robot.port=/dev/ttyACM0 \
     --robot.id=rlinf_follower

Replace the port with your device. Move the joints to the middle positions
shown in the guide, confirm the prompt, then move each joint through its travel
as instructed. The tool reports the saved calibration file. Keep it under the
account used for RLinf and reuse the ID as
``--id rlinf_follower``; do not substitute the leader's calibration.

.. warning::

   RLinf workers do not run interactive follower calibration. Missing or
   inconsistent calibration causes connection to fail. Calibrate under the
   account that will run the arm before starting workers.

Run It
------

With the follower calibrated, use the interactive test to check its joints and
gripper. The script may start a local Ray instance to communicate with the arm.

.. warning::

   On hardware, startup moves all six servos to the standard state. The joint
   target is approximately ``[-4, -63.8, 33.6, 83.6, -91.8]`` degrees and the
   gripper target is ``0.013`` on the ``0..1`` opening scale. Clear both arms'
   motion paths before launching the toolkit. Pass ``--no-reset`` to connect
   without commanding startup movement.

With the follower calibrated and room for the reset trajectory, run:

.. code-block:: bash

   CAMERA_SERIALS='' python -m toolkits.realworld_check.test_so101_env \
     --port /dev/ttyACM0 --id rlinf_follower --step 2

Replace the port with your device and use the ID from calibration.
``CAMERA_SERIALS=''`` disables camera discovery so the check uses only the arm.

Startup reset and the ``home`` command move the joints and gripper to the
standard state. They use a smooth trajectory from the measured joint positions,
with a default commanded speed limit of 30 degrees per second. Use
``--reset-speed 10`` for a slower reset. In an environment config,
``reset_joint_qpos`` and ``reset_gripper_position`` define the complete state,
``reset_joint_speed`` uses radians per second, and ``reset_duration`` sets the
minimum trajectory duration.

Enter these commands one at a time, allowing each move to finish:

.. code-block:: text

   where
   up
   down
   open
   close
   park
   quit

``up`` and ``down`` change the shoulder angle by two degrees, rather than moving
the tool vertically. Joint feedback is printed after each move; ``open`` and
``close`` test the gripper. Run ``park`` when you want to move to the configured
folded state, then use ``quit`` to close the environment and its arm worker.
Closing a session only releases its resources. Use ``help`` for the other joint
directions.

To use the arm in your own program or attach cameras, see
:doc:`Robotics Interface </rst_source/concepts/robotics>`.

Follow a Leader Arm
-------------------

To control the follower by hand, connect and calibrate an SO101 leader using
its own port and calibration ID:

.. code-block:: bash

   lerobot-calibrate \
     --teleop.type=so101_leader \
     --teleop.port=/dev/ttyACM1 \
     --teleop.id=rlinf_leader

Start the check with both arms configured. Camera discovery is enabled when
``CAMERA_SERIALS`` is unset; add ``--enable-camera-player`` to display images:

.. code-block:: bash

   python -m toolkits.realworld_check.test_so101_env \
     --port /dev/ttyACM0 --id rlinf_follower \
     --leader /dev/ttyACM1 --leader-id rlinf_leader \
     --fps 30 --enable-camera-player

After the follower reaches its standard state, place the leader in a matching pose and enter
``teleop``. The follower tracks both the joints and gripper continuously.
Press Ctrl-C once to return to the prompt, then enter ``quit`` to disconnect.

``--fps`` sets the requested control rate and defaults to 30 Hz. Camera capture
runs independently; the environment reuses frames up to ``camera_max_age``
seconds old (default 0.5) instead of waiting for a new image at every step.
Continuous gripper commands return without waiting for travel. The driver
monitors stalled jaws and holds them at the measured opening to relieve
pressure. Each measured advance toward the target restarts stall detection,
so slow or sustained movement can continue while it makes progress.
Move the leader's gripper away from that opening before retrying
motion into the obstruction. The driver's ``open_gripper()`` and
``close_gripper()`` methods still wait for travel or stall relief.

Collect Demonstrations
----------------------

Once both arms pass the checks, use the SO-101 collection config to give every
recorded episode the same starting state. Edit the follower and leader ports and
calibration IDs in
``examples/embodiment/config/realworld_so101_collect_data_joint.yaml``, then run:

.. code-block:: bash

   bash examples/embodiment/collect_data.sh \
     realworld_so101_collect_data_joint

Linux hosts without ``/dev/input``, including WSL, can use a control file
instead of an evdev keyboard. Set the file before launching collection:

.. code-block:: bash

   export RLINF_KEYBOARD_CONTROL_FILE=/tmp/rlinf_so101_control
   : > "$RLINF_KEYBOARD_CONTROL_FILE"
   bash examples/embodiment/collect_data.sh \
     realworld_so101_collect_data_joint

Append commands from another terminal. Each command is consumed once:

.. code-block:: bash

   echo start >> /tmp/rlinf_so101_control
   echo segment >> /tmp/rlinf_so101_control
   echo success >> /tmp/rlinf_so101_control

``abort`` stops the current recording without moving the robot. The same input
backend accepts ``failure`` during evaluation and ``intervene`` / ``release``
for explicit DAgger control.

The first reset and every episode reset start the leader and follower
trajectories together. Both arms move their five joints and grippers to the
configured standard state. After both trajectories finish, the leader holds
that state for ``reset_hold_seconds`` and then releases torque for the operator.
The foot-pedal ``start_end`` controls recording: ``a`` starts or aborts the
current recording, ``b`` advances the segment, and ``c`` saves the episode as a
success. The config writes the finalized LeRobot dataset below the run's
``collected_data`` directory.

If collection raises an error, the runner moves the leader and follower to
their configured park state together, then closes both connections and releases
torque. A failure during that safety motion is logged while cleanup continues.

The park state is an explicit operation. Use ``park`` in the interactive check
when you need it; ending collection or calling ``close()`` only releases the
devices.

New Real-World Tasks
--------------------

After the hardware checks pass, follow
:doc:`New Real-World Tasks </rst_source/extending/new_task>` to define a task's
reset procedure, observations, actions, reward, and success condition. A working
real-world task is required before starting training.
