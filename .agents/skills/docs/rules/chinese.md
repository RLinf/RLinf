# 中文写作规范

中文页面应当读起来像一位以中文为母语的工程师写给同行的技术文档，而不是英文页面的译文。本文件规定 RLinf 中文文档的写法，PR 描述、评审意见等中文写作同样适用。页面类型的要求见对应的类型文件，术语译法见 [glossary.md](glossary.md)。

## 先理解，再用中文写

中英文页面的结构保持一致：章节、命令、配置项、数字和链接都相同，句子不必一一对应。动笔前先想清楚这一段要告诉读者什么，可以从页面提纲出发，也可以先读懂整段英文；然后按中文的习惯组织句子，可以拆句、合句、调整语序，删掉只为套用英文句式而存在的词。英文靠连词把从句串起来，中文靠短句和动词推进，句子之间的关系往往不必写出来。

- 英文：It will also be updated whenever the source changes.
- 翻译腔：每当源发生改变的时候，它也将会被更新。
- 中文：源数据一变，它就跟着更新。

## 排版

- 中文句子使用全角标点：，。、；：？！“”（）——……。整句都是英文时保留半角标点。
- 引号统一用 “”，引号里再嵌套时用 ‘’，不用「」。
- 中文与英文、中文与数字之间加一个半角空格，例如：在 4 张 GPU 上训练 ``maniskill_libero`` 环境。数字与单位之间也加空格（80 GB、10 Gbps），% 和 ° 前不加。
- 全角标点前后不加空格。
- 并列的词用顿号分隔，英文词也一样：LIBERO、ManiSkill、RoboTwin。
- 英文专有名词保持原有大小写（GitHub、PyTorch、ManiSkill），英文词不写复数：“多个 worker”，不写“多个 workers”。
- 段落和列表项的正文在 RST 源文件里各占一行，不按列宽换行：RST 会把段内换行渲染成空格，两个汉字之间会多出一个空隙。
- 行内代码或加粗紧挨全角标点或汉字时，用转义空格（反斜杠加空格）隔开，否则会构建失败或渲染出错，写法见 [../reference.md](../reference.md#inline-markup-next-to-cjk-punctuation)。

## 术语

- 代码里的名字一律保留原文，不翻译：配置项、命令、参数、脚本名、环境名、模型名。
- 开发者日常就用英文说的词保留英文，例如 policy、rollout、worker、actor、critic、checkpoint、key、value、endpoint、schema、API。第一次出现时用中文交代它在这里指什么，之后直接用。
- 已有通行中文说法的用通行说法：显存、训练、推理、微调、数据集、权重、配置项。
- 强化学习里的 policy 写作 policy，不译作“策略”；泛指的方法仍可以叫“策略”，例如“placement 策略”。rollout 不译作“展开”。
- 同一个概念全文只用一个词，不在“环境”“仿真环境”“模拟器”之间来回换。

## 句子

- 一句话说一件事，一个分句一般不超过 40 个字；一逗到底的长句拆成两三句。
- 用主动句，让做事的一方作主语：“启动器读取配置文件”，不写“配置文件被启动器读取”。“被”字句在中文里常带不如意的意味，确实需要强调受事时再用。
- 删掉空动词：“对模型进行训练”写成“训练模型”，“实现了对多节点的支持”写成“支持多节点”，“提供了……的能力”写成“可以……”。
- 不照搬英文的连接结构：
  - when：“当……时”多数可以去掉，或改成“……后”“……时”：“当训练开始时，日志会……”写成“训练开始后，日志会……”。
  - for、regarding：“对于每个环境来说”写成“每个环境”；“关于”“有关”多半可以删。
  - through、by：“通过……的方式”改成直接说怎么做。
  - allow、enable：“允许你……”“使……能够……”写成“可以……”。
  - based on：“基于……”只在确实是基础时用，其余写“用”“按”“根据”。
- 不补英文的冠词和代词：删掉多余的“一个”“它”“你的”“其”。“调整你的应用程序的一些功能”写成“调整应用程序的一些功能”。指代不清时，重复名词，不用“其”“该”“此”。
- “的”不要连用；能删的“的”删掉：“许多的相同的操作”写成“许多相同的操作”。
- 用具体数字代替程度词：“性能显著提升”写成“吞吐提高到原来的 1.8 倍”。
- 量词用对：两位研究人员、三台机器，不一律用“个”；“们”不和“都”“各”重复。

## 语气

- 书面、清楚、克制。不写聊天式的口语（“看看长什么样”“等需要时再看”“不用跟着改”），也不写公文腔（“本文旨在”“进行相关操作”“倘若”“若要”）。
- 称呼读者用“你”，或者省略主语；不用“您”。概念页讲解示例时可以少量用“我们”，例如“我们先从一台机械臂开始”。
- 不夸张，不用“最佳”“最先进”“强大”“无缝”“完美”“一站式”。
- 不用“值得注意的是”“需要注意的是”开头。要提醒的内容放进 warning 或 note，或者直接写出事实。
- 不用“首先……其次……最后……”串起每一句。步骤写成有序列表，句子之间靠事情本身的先后连接。
- 少用破折号连接普通分句，改用逗号、冒号或断句。
- 不写“不是……而是……”式的对比，除非读者真的会那样误解。
- 不加“本节将介绍”“接下来我们来看”之类的预告，直接写内容。

## 标题和列表

- 标题短，写任务或概念，任务标题用“动词 + 对象”：“安装依赖”“配置多节点训练”。标题末尾不加标点，不直译英文的动名词（“Using Collaboration”写成“使用协作功能”，不写“正在使用协作功能”）。
- 列表前用一句话引出。列表项结构一致；全是句子时句末加句号，全是短语时不加。
- 只有顺序重要时才用有序列表。

## 各类页面的中文写法

- **示例页**：开头一句说明这一页带你跑通什么、得到什么结果。步骤标题用“动词 + 对象”，标准章节名是 概览、任务、观测与动作、安装、下载模型、运行、可视化与结果。每条命令前用一句话说明它做什么，命令后给出预期输出或成功的标志。不讲内部实现。
- **指南页**：先说在什么情况下需要它、做完后有什么变化，再按步骤写，只列出读者要写的配置项。
- **概念页**：开头一两句说清它是什么、解决什么问题。先用中文把机制讲明白，再给出读者可以在代码里搜索的英文名称。段落之间要有自然的过渡，可以用“先……再……”“有了这一层……”带着读者往下走，但不要每段都用同一种过渡。
- **Robotics 文档**：机械臂、夹爪、相机等 ``RobotPart`` 统一叫“零部件”；``action_parts`` 中的 part 按语境写成“动作项”或“对应的机器人动作”。介绍组合模型时说“零部件的名称、层级和访问路径”，不写“按名称组织的部件树”这类抽象说法；``parts`` 和 ``children`` 保留原文，分别解释为 connection 支持的零部件和组合中的直接下一级。

## 常见翻译腔，对照改写

| 翻译腔 | 中文 |
|---|---|
| 该脚本被用来启动训练。 | 这个脚本用来启动训练。 |
| 它允许你在多个节点上运行训练。 | 可以在多个节点上训练。 |
| 对于每一个环境来说，…… | 每个环境…… |
| 配置文件由 env worker 负责读取。 | env worker 读取配置文件。 |
| 这就是全部的接入工作。 | 接入到此完成。 |
| 当你把模型下载好了之后，运行下面的命令。 | 模型下载完成后，运行下面的命令。 |
| 对模型进行评估。 | 评估模型。 |
| 值得注意的是，显存需要至少 40 GB。 | 显存至少需要 40 GB。 |
| 首先，克隆仓库。其次，安装依赖。最后，运行脚本。 | 克隆仓库、安装依赖后，运行脚本。 |
| RLinf 不仅仅是一个训练框架，更是一个…… | 删去，直接说它做什么。 |
| 本节将介绍如何配置 placement。 | 删去，直接开始写怎么配置。 |
| 通过修改配置文件的方式来调整并行度。 | 修改配置文件，调整并行度。 |
| 这使得用户能够更方便地进行调试。 | 这样调试更方便。 |
| 2 个研究人员 | 两位研究人员 |
